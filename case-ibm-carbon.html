Fourteen product squads were hard-coding colours and rebuilding the same components. I set up a token pipeline and a contribution council so design changes reached production automatically.

01

The problem

Situation

Fourteen squads built on Carbon, but each one had drifted. We found 320+ hard-coded colour values and several versions of the same button.

Brand or theme changes took about four weeks to reach code, and 70% of front-end QA tickets were visual bugs.

02

My role and how I led

What I did myself, and what I trusted the team with

What I owned

  • Ran the drift audit and made the case to engineering leadership
  • Defined the three-tier token structure with the DesignOps lead
  • Set up and chaired the weekly contribution council
  • Agreed success metrics with front-end leads

What I delegated

  • Figma variables and token library: DesignOps designers
  • CI pipeline (Style Dictionary + GitHub Actions): front-end engineers
  • Visual regression and accessibility checks: QA with DesignOps
  • RFC templates and council admin: rotating squad representatives
03

Process

From research to measured outcome

01

Audit

Inventoried colours, spacing and components across 14 squads.

02

Define

Three token tiers: global → semantic → component.

03

Design

Figma variables with light and dark modes from day one.

04

Build

Publishing a token opens pull requests in every squad repo automatically.

05

Govern

Squads propose changes with a one-page RFC; council reviews weekly.

06

Measure

Visual QA bugs, handoff time and front-end velocity per sprint.

04

Evidence

Artifacts from the project

05

Key decisions

The calls I made and what they cost

1

Semantic tokens between brand and components

Why: Squads should change “primary action”, not “blue-60”.

Trade-off: A learning curve for designers used to picking colours directly.

2

A council, not a central gatekeeper

Why: A small central team would become a bottleneck for 14 squads.

Trade-off: Slower for one-off requests; faster for everyone overall.

3

Automate pull requests instead of writing docs

Why: Docs go stale; automated PRs make the right thing the easy thing.

Trade-off: Needed engineering time up front from two front-end engineers.

06

Results

Business and user impact

Design-to-code handoff dropped from about four weeks to a day, visual QA bugs fell 70%, and front-end velocity rose 28%. Light and dark themes now stay in sync automatically.

07

What I learned

A design system is a product, and its customers are engineers. Treating squads as users, with research and release notes, is what got adoption.
